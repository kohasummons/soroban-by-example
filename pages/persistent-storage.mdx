## Guide

`#![no_std]` This attribute prevents linking to the standard library, making the code lighter and more efficient for Soroban contracts. It's big so we save on size.

`use soroban_sdk::{contract, contractimpl, Env, log}`  Imports stuffs from the Soroban SDK. `Env` is basic Soroban type, we need it because we can't use the Rust standard library.

`#[contracttype]` Used to define the type of a contract. It's essential for specifying the contract's capabilities, permissions, and the kind of interactions it can have with other contracts or with the blockchain itself.

`#[contract]`  Marks the struct as a Soroban smart contract. Soroban smart contracts are defined as Rust structs.

`#[contractimpl]` Marks the implementation block as containing contract methods and transforms it to code that Soroban can evaluate directly

`pub` Marks a function as external, meaning it can be invoked outside of the context of the contract code it
self.

## Explanation

Persistent storage is for data that must outlive a single invocation and survive contract upgrades: balances, ownership, user records. Every entry is addressed by a key; here the keys live in the `DataKey` enum so they are all in one place. A variant can carry data, which is how `Profile(Address)` gives every user their own slot.

Any type that implements the SDK's storage traits can be stored, and the API is the same for all of them:

- **Primitives** (`u32`, `i128`, `bool`) — `increment` reads with `get`, falls back with `unwrap_or`, and writes with `set`.
- **`String`** — `set_greeting` / `get_greeting`. `get` returns `Option`, so a missing value is `None` rather than a panic.
- **`Address`** — `set_owner` stores the caller after `require_auth`, the usual way to record who controls a contract.
- **`Vec`** — collections are values, not references. `add_score` loads the whole `Vec`, pushes, and writes it back.
- **`Map`** — `credit` and `balance_of` do the same load–update–store cycle with a `Map<Symbol, i128>`.
- **Structs** — anything marked `#[contracttype]` stores directly; `set_profile` writes a `Profile` under a per-user key.

`has` checks whether a key exists without deserialising the value, and `remove` deletes an entry (and stops paying rent for it).

### TTL

Persistent entries are archived when their TTL runs out, so every write is followed by `extend_ttl(&key, TTL_THRESHOLD, TTL_EXTEND_TO)`: if fewer than 1000 ledgers remain, top the entry up to 5000. Reads do not need it, but anything that should stay live must be extended somewhere on its write path.
